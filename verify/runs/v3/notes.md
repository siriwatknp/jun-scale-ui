# Notes on scale.css

## How the file is built

- `--scale` and `--scale-group1` to `--scale-group7` are registered with `@property` as `<number>`, inherited, with an initial value of 1. This gives rule 3 ("It is 1 unless set") and rule 5 ("A value that is not a valid number is ignored. The valid value set further out applies instead"). In Chromium, an invalid value such as `--scale: abc` is dropped when values are computed, and the element takes the value from its parent. I checked this: a `StatusDot` under `--scale: 2` and then `--scale: abc` renders at 16px.
- Each component works out its effective scale once, on its own root, in a private property named after it: `--Button-scale: calc(var(--scale, 1) * var(--scale-group5, 1))`. Parts read that property. This is the pattern rule 9 allows ("Working out a component's effective scale once, on the component's own root ... is fine"). Using one name per component, not one shared name, means a rule written by a parent for a child can still reach the parent's scale (rule 8, second bullet). No fixture needed that in the end.
- Every size is written as `calc(<base>px * var(--X-scale))` in the property that uses it. No scaled size is stored in a shared value (rule 9).
- All boxes use `box-sizing: border-box`, so base sizes are outer sizes and the 1px borders do not scale (rule 2).
- All component rules sit in `@layer components`. A user rule on the component element without a layer then beats the component's own factor default, even when it has the same specificity. This is how I read rule 7: "A factor a user sets on the component element itself wins over the default the component sets." Inline styles win either way.
- Children are centered with flex or grid alignment, never with fixed offsets (rule 8, third bullet).

## Sizes and factors I chose for inner parts

| Component | Inner part or child | Choice | Why |
| --- | --- | --- | --- |
| Checkbox | `Icon` checkmark | `--scale-group2: 0.5` on `.Checkbox`, giving 8px | Rule 10 gives this exact case: "A 16px `Icon` centered in a 16px box needs 0.5, which gives 8px." 0.75 would give 12px, only 4px smaller. |
| Checkbox | `.Checkbox-input` | Fills the 16×16 root, `appearance: none`, draws the box, border and radius. The `Icon` sits in the same grid cell and is centered with `place-self: center`. It is hidden when the input is not checked. | The visible box has to be a real box (the "Part" definition forbids painted shapes). Stacking both in one grid cell centers by layout. |
| Radio | dot, `::before` | 8×8, centered with `place-content: center` on the input | 16 − 8 = 8, a multiple of 8. Drawn only when `:checked`. |
| Switch | thumb, `::before` | 16×16 circle. The track has 4px padding on the left and centers the thumb vertically. When checked, the thumb moves right with `translate: 16px × scale`. | 24 − 16 = 8, so the gap is 4px on top, bottom and left. A 16px move leaves the same 4px gap on the right. |
| Switch | track radius | 12px × scale, half the track height | "Fully rounded" with a scaled radius instead of a huge fixed value. |
| Select | `Avatar` | `--scale-group4: 0.75` on `.Select`, giving 24px | Rule 10 gives this exact case: "A 32px `Avatar` centered in a 32px box can take 0.75, which gives 24px." It is set on the root `.Select`, not on the trigger part, as rule 7 requires. |
| Select | chevron `Icon` | Full size (16px), with `margin-inline-start: auto` | The brief says the chevron is "at the end". The trigger has no width, so `auto` only matters if someone gives it one. |
| Callout | `Icon` | `--scale-group2: 0.75` on `.Callout`, giving 12px | Rule 10: "A 16px `Icon` centered on a 20px text line needs 0.75, which gives 12px." |
| Callout | centering on the first line | Grid with columns `auto 1fr` and rows `20px × scale` then `auto`. The icon sits in row 1 with `align-self: center`. The text spans both rows. | This centers the icon on the first line by layout. If a user changes the `Icon` factor, the icon stays centered. |
| Input | `.Input-field` | `flex: 1`, stretched to the full inner height, no border or background | A 20px field centered in a 32px box would differ by 12px, not a multiple of 8. Stretching avoids that. The browser centers the text inside, and text is exempt. |
| Field | `Input` | `.Field > .Input { width: auto }`, so the column stretches it to the Field width | The brief says the Input "stretches to the Field's width". `auto` is not a base size, so nothing needs scaling. |
| Button | `Icon` | No factor, so 16px | The brief says "at full size". 32 − 16 = 16. |

Decoration that I did not scale: the Switch thumb shadow, and the 2px focus outline on `Input`. Rule 2 allows either.

## Checks I ran

I served the folder locally and measured it in headless Chromium with `playwright-cli`. At `--scale: 1` and `1.5` every box matches the brief. For example, at 1.5: `Button` 48px tall with a 24px icon, `Input` 270×48, `Select` avatar 36px in a 48px trigger, `Callout` 270px wide with an 18px icon. All checked inner offsets are whole pixels. At `--scale: 1.25` the Callout icon is 15px and sits 5px below the top of a 25px line. A screenshot of the fixtures is in `screenshot.png`.

I also checked these cases with markup added only in the browser. `fixtures.html` is unchanged.

- A factor on a container further out (`--scale-group2: 2`) does not change the Checkbox icon. It stays 8px, because the Checkbox's own default is nearer.
- `--scale: 2; --scale-group4: 1` on `.Select-trigger` leaves the trigger at 32px. The Avatar inside grows to 64px and the chevron to 32px. This matches rule 8: setting a value on a part "only changes components inside the part".
- `--scale-group5: 0.5` under `--scale: 2` makes a Button 32px tall, while its Icon stays at 32px. This follows rule 6: "An `Icon` inside a `Button` keeps its own group factor when the `Button` shrinks."

## Places where PRINCIPLE.md was unclear, incomplete, or in tension

1. **An invalid factor on an element that also has the component's default.** Rule 5 says: "A value that is not a valid number is ignored. The valid value set further out applies instead." Rule 7 says the component's default on its own root beats a container further out. It is not clear what happens when a user writes `style="--scale-group2: xyz"` on a `.Checkbox`. Is the component's default (0.5, on the same element) "further out"? With `@property`, the inline value wins the cascade, then fails, and the element takes its parent's value. I tested this: under a container with `--scale-group2: 1.5`, the checkmark became 24px inside a 16px box. That is the literal reading of "further out", but it is probably not what anyone wants. Plain CSS cannot fall back to a lower-priority declaration on the same element, so I left it and am noting it.
2. **Invalid values need `@property`.** Rule 5's fallback cannot be met with unregistered custom properties. An invalid unregistered value breaks every `calc()` that uses it. The principle says it describes "what must be true, not how", but this one rule quietly decides the method. It also ties support to browsers with `@property`. I added `var(--scale, 1)` fallbacks, which only cover the case where nothing is set.
3. **Centering on a text line is not centering in a box.** Rule 8 says: "When a child component must be centered inside a box of its parent, center it with layout alignment rather than a fixed offset." The Callout icon must be centered on "the first 20px text line", and a line is not a box. To use layout alignment I had to make a box of one line height: a grid row of `20px × scale`. Rule 10 talks about "the box or text line it is centered in", so text lines are expected. Rule 8 does not say how to center on one by layout.
4. **Rule 2's list of scaled properties is incomplete.** It lists "width, height, minimum and maximum width and height, margin, padding, gap, position offsets ... font size, line height and border radius". It does not mention grid track sizes, `flex-basis`, or `row-gap`/`column-gap` by name. I scaled the Callout grid row and used `column-gap`. I took "gap" to cover both, and assumed any length that sets a box size scales.
5. **The fixture goes against the user advice in rule 10.** Rule 10 says to pick factors that land on multiples of 4px, "but not 0.5 for a 20px `Badge`, which gives 10px". The `ButtonWithBadge` fixture sets exactly `--scale-group3: 0.5`. I kept it as the brief asks. The result: the Badge is 10px tall with 6px text on an 8px line at scale 1. At scale 1.5 it is 15px tall in a 48px Button, so it sits half a pixel off (measured top offset 16.5px). Rule 10 allows this ("a centered child can then be 1px off"), but the fixture's purpose is not stated. It could be a test of the 1px-off case or a mistake.
6. **The "multiple of 8px" rule only holds at scale 1.** Rule 10 says a centered box "differs from it by a multiple of 8px, so the gap on each side is a multiple of 4px". At `--scale: 1.5`, the Checkbox icon is 12px in a 24px box (12px apart), and the Select avatar is 36px in a 48px trigger (12px apart). Edges still land on whole pixels, which is the real goal. The rule reads as if it applies at every scale, but it can only apply to base sizes.
7. **Borders and the centering arithmetic.** Rule 2 says a 1px border "does not change where its centered content lands", and rule 10 counts the 8px difference against the outer box. With a 1px border on both sides, the inner space is 2px smaller, so the real gap is 3px, not 4px (Checkbox, Radio, Select). This is whole pixels, so nothing breaks, but "the gap on each side is a multiple of 4px" is not literally true for bordered boxes.
8. **Overflow when only the parent shrinks.** Rule 6 makes an `Icon` keep its size when a `Button` shrinks. A Button at group factor 0.5 therefore has a 16px icon in a 16px-tall box, with no room left. The same happens to the Select avatar when a user sets `--scale` on the trigger part. The principle allows this and gives no guidance on overflow. I did not add clipping.
9. **The "Inline" group range versus factors set by parents.** Rule 4 gives group 3 a base size of "16–24px", and the table only describes base sizes. It is not said whether a component can be pushed far outside its group's range by factors (the 10px Badge in item 5). I read the table as describing base sizes only.
10. **Where the Select's group 5 size lives.** Rule 4 says the base size column is "the height of the component's main box". For `Select`, the brief puts all sizes on the trigger part, and the `.Select` root has none. I read "main box" as the trigger, and the root is just a wrapper that holds the factor. The principle does not say a component's main box can be a part.
11. **Switch checked position.** The brief only says the thumb is "inset by the same gap on the top, bottom and left". It does not describe the checked state. I moved the thumb 16px (scaled) so it keeps a 4px gap on the right.
12. **Valid ranges are not defined.** Rule 3 says `--scale` "is a number". Zero and negative numbers are valid `<number>` values and pass through. Zero collapses components and negative values give invalid sizes. The principle does not say whether these count as "not a valid number".
