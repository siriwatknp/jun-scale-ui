# Notes on scale.css

## What I built

`scale.css` styles the components in `fixtures.html`: StatusDot, Icon, Badge, Checkbox, Radio, Switch, Avatar, Button, Input, Select (trigger only), Field (label, help, error) and Callout. I skipped Kbd, Spinner, IconButton, Combobox, TextArea, Slider, Progress, DropdownMenu, Popup, `Input-action` and the Field group, addon, option and layout variants, because no fixture uses them and the brief says to build only the fixture components.

`shot.png` is a screenshot of the fixtures at the end of the work.

## Decisions

1. **Effective scale on the component root.** Every component root declares two private values: `--_factor` (its own group factor, `var(--scale-groupN, 1)`) and `--_scale` (`var(--scale, 1) × --_factor`). Every size on the root and on its parts is `base × var(--_scale)`. Parts never read `--scale` or a group factor themselves, so setting one on a part does not change the part (rule 8). Both private values are registered with `@property` as inherited numbers. Registration is not required for correctness, but it keeps the inherited value a plain number.
2. **Passing factors down.** Each component root sets `--scale-group1` up to `--scale-group(N-1)` to `var(--_factor)`, times a default where `SPEC.md` gives one: Checkbox sets group 2 to 0.5, Callout sets group 2 to 0.75. When the default applies inside one part only, the part sets it from the root's `--_factor`: `Select-trigger` sets group 4 to 0.75, and `Field-label`, `Field-help` and `Field-error` set group 3 to 0.8. No component sets its own group's factor.
3. **User overrides.** A factor set in an inline style on the component element wins over the stylesheet, so `--scale-group2: 1` on the Checkbox and `--scale-group3: 0.5` on the Button are used as they are (rule 7, last bullet).
4. **Outer sizes.** All components and parts use `box-sizing: border-box`, so a 32px Input with a 1px border is 32px tall in total. Borders and outlines are 1px and never scale.
5. **Centering.** Children are centered with flex or grid alignment, never with a fixed offset (rule 8). The Checkbox stacks its input and checkmark in one grid cell with `place-items: center`. The Radio dot is a `::before` on the input, centered by grid.
6. **Callout icon on the first line.** The Callout is a grid whose first row is exactly one text line tall (`20px × scale`). The text spans both rows, and the Icon sits in the first row with `align-self: center`. That centers the Icon on the first line with layout alignment, so it stays centered if a user changes the Icon factor.
7. **Switch thumb.** The thumb is a `::before` part, placed with `top` and `left` at 4 and moved with `translate` 16 when checked. It is a part, not a child component, so fixed offsets are allowed. All three values scale.
8. **Checkbox structure.** `Checkbox-input` draws the 1px border, radius and checked fill, with `appearance: none`, and fills the 16×16 span. The checkmark Icon is hidden with `visibility` when the input is not checked.
9. **Field stretching.** An Input or Select directly inside a Field gets `width: auto` (the Select trigger gets 100%), so it fills the 240px Field.
10. **Borders and colors.** `SPEC.md` gives no border for Button, Badge, Avatar, Switch or Callout, so they have none and use a fill. Colors are neutral grays with one blue accent. Native margins and paddings on `input`, `button` and `p` are reset to 0, since a fixed native margin would not scale.

## Checks I ran

I measured the fixtures in a headless browser at `--scale` 1, 1.25 and 1.5:

- Every base size matches `SPEC.md` at scale 1 and is exactly 1.5× at scale 1.5. Examples: Button 32 → 48, Input 180×32 → 270×48, Field 240 → 360, Callout icon 12 → 18.
- Centered children land on whole pixels: the Checkbox checkmark is 4px in at scale 1, 5px at 1.25 and 6px at 1.5. The Select Avatar is 24 in a 32 trigger (4 above and below). The Callout icon is 4px below the first line's top at scale 1 and 6px at 1.5.
- `--scale-group2: 1.5` on a cell around a Button leaves the Button's icon at 16 (the Button sets that factor nearer). `--scale-group5: 1.5` on the cell gives a 48px Button with a 24px icon. `--scale: 1.25` with `--scale-group5: 1.2` gives 48 and 24.
- `--scale: 2` on `Select-trigger` leaves the trigger at 32px tall, but the Avatar inside grows to 48px. `--scale-group5: 2` on the trigger changes nothing.
- A Badge added into `Field-label` renders 16px tall; a Checkbox added next to the label stays 16px.

## Unclear points, gaps and contradictions

1. **Default factor 0.8 in Field breaks the whole-pixel rule.** PRINCIPLE rule 10 says: "Every default factor that a component sets is chosen for the child it is designed around: it keeps that child's box sizes on multiples of 4px". SPEC sets "Inline 0.8 in `Field-label`, `Field-help` and `Field-error`". At scale 1 that gives a Badge with 6.4px padding and a 3.2px gap (I measured a 31.02px wide Badge), a 12.8px Checkbox and a 19.2px Switch. Only the Badge's 20px height lands on 16. Rule 10 also promises "Every size the components define then lands on a whole pixel, including sizes changed by the factors components set themselves", which is false here at scale 1. I implemented 0.8 as written.
2. **The ButtonScaled fixture breaks the user rules in rule 10.** Rule 10 says to "keep the product of the values you set in steps of 0.25" and to pick a group factor "that keeps that group's base sizes on multiples of 4px". The fixture sets `--scale-group5: 1.2` under `--scale: 1` and `--scale: 1.5`, which gives 1.2 and 1.8. The Button is 38.4px and 57.6px tall and its icon 19.2px and 28.8px. The rule 10 example only blesses 1.2 together with `--scale: 1.25`. I rendered the fixture as given; the fractional sizes are expected.
3. **The ButtonWithBadge fixture also falls outside the rules.** `--scale-group3: 0.5` makes the Badge 10px tall with 4px padding and 6px text. At `--scale: 1.5` the Badge is 15px in a 48px Button, so it sits half a pixel off. `SPEC.md`'s accepted deviations only cover a 20px Badge in a 32px box under one shared factor, not a user factor that takes group 3 off the 4px grid.
4. **Which group factor a part multiplies by.** Rule 7 says a part that sets a default does so "still multiplied by the component's own group factor". It does not say whether that is the factor at the component root or the factor in force at the part. They differ when a user sets `--scale-group5` on the part. I used the root's value, to match rule 8 ("Setting --scale or a group factor on a part does not change the part itself").
5. **Computing the scale on the root is required, not optional.** Rule 9 says computing the effective scale once on the root "is fine". Rule 8 can only hold if parts never read `--scale` themselves, so this is the only correct option. The principle also never says that this needs a private variable name, while "What users write" lists only `--scale` and `--scale-group<N>`. I used `--_factor` and `--_scale`.
6. **Odd result of rule 8 for `--scale` on a part.** "Setting `--scale` or a group factor on a part does not change the part itself. A component inside the part reads `--scale` ... at the nearest element that sets them". So `--scale: 2` on `Select-trigger` keeps the trigger at 32px but grows its Avatar to 48px, which overflows. I followed the rule, but it is unlikely to be what a user wants.
7. **Where "Avatar 0.75 in the trigger" is set.** Rule 7 says defaults go on the component root, unless "only the children inside one part need a different default". SPEC says "Avatar 0.75 in the trigger", which reads as a part default. I set it on `Select-trigger`, so an Avatar in the Popup would be full size. SPEC does not say whether Popup items can hold Avatars or what size they should be.
8. **Does padding include the border?** Rule 2 says borders "are not part of the base size arithmetic: a 1px border on both sides of a box does not change where its centered content lands". That covers centered content only. For start-aligned content, SPEC's "padding 8 left and right" on Input could mean 8px from the outer edge or 8px inside the border. I used CSS's normal behavior, so the Input icon starts 9px from the outer edge and the Select Avatar 13px.
9. **Which element of the Checkbox has the border.** SPEC says "16×16 box, 1px border, radius 3" and "`Checkbox-input` fills the box", but not whether the border belongs to the `Checkbox` span or to `Checkbox-input`. I put it on the input. Either choice gives the same size and center.
10. **Centering a child on the first text line.** SPEC asks for "an Icon centered on the first text line" in Callout, and rule 8 forbids a fixed offset for child components. Neither document says how to do this in CSS. I used the grid row trick in Decision 6. If a user sets the Icon factor bigger than one line, the Icon overflows its row evenly above and below.
11. **Fixed offsets in SPEC conflict with rule 8.** SPEC's inline Field layout says "A Checkbox sits 4 below the top of that line" of 24. That is a fixed offset for a child component, which rule 8 forbids, and it is only centered while the Checkbox is 16px. I did not build that layout, but an implementer would have to choose between the two documents. `Input-action` "4 past the right padding" is similarly unclear: it may be a negative margin into the padding, or extra space.
12. **Groups are not ordered by size.** Rule 4 says "A bigger number holds bigger components", and the SPEC table gives group 5 a base size of "32–64px". Yet Slider (20px tall) and Progress (8px tall) are in group 5, smaller than the 24px Switch in group 3.
13. **The 1px Popup separator.** Rule 10 says "Every base size and offset of a box is a multiple of 4px", and rule 2 says heights scale. SPEC gives `Popup-separator` as "1px tall", which is neither a multiple of 4 nor clearly a border. If it scales, it is 1.25px at scale 1.25. I did not build it.
14. **Spinner's 2px ring.** SPEC says "2px ring". If the ring is a border, rule 2 says it does not scale. If it is an SVG stroke, rule 2 says it scales. Not built, but the spec does not say which.
15. **The spacing list in SPEC is incomplete.** "Spacing and box sizes come from multiples of 4px: 4, 8, 12, 16, 24, 32, 40, 48, 64" leaves out sizes the same spec uses, such as 20, 80, 128, 160, 180 and 240. I read the list as examples and "multiples of 4px" as the rule.
16. **Does `--scale` on a component apply to the component itself?** Rule 3 says it "applies to every component inside that element", and rule 6 says "A value set on an element applies inside that element". Read literally, a value on a component's own element would not apply to that component, but rule 7 says a factor set on the component element is used. I applied values on the component's own element to the component.
17. **Text line heights.** Rule 2 lists line height among the sizes that scale, and SPEC gives line heights in px ("12px on a 16px line"). I wrote them as `px × scale`, not unitless ratios, so a 20px line is 25px at scale 1.25. Rule 10 exempts that from the 4px grid, but the documents could say directly that line heights are lengths, not ratios.
